### Route Architecture

- `src/app/admin/layout.tsx` renders `AdminWorkspace` for canonical Admin workspace paths. Section pages are route-segment markers and the workspace derives the active section from `src/lib/admin-routes.ts`.
- `src/app/admin/brokers/[userId]/layout.tsx` renders `AdminBrokerDetailWorkspace`; child segments select overview/listings/requirements/enquiries/activity.
- `middleware.ts` converts legacy Admin tab query navigation to route segments. Do not generate legacy query URLs.
- `src/app/dashboard/page.tsx` redirects legacy section query navigation to route segments. Dashboard child pages render `DashboardSectionPage` with one section ID.

## Workspace Data Architecture

### Dashboard

- `DashboardSectionPageClient.tsx` fetches `/api/dashboard/shell` plus only the active section endpoint.
- Profile uses shell data and `/api/dashboard/profile`; notifications load independently through the notification hook.
- `src/lib/broker-dashboard-server.ts` contains section fetchers, dashboard metrics, bounded recent overview data, and compatibility assembly.

### Admin

- `AdminWorkspace.tsx` always loads lightweight overview and site-mode context, then enables only the active list/chat/activity endpoint.
- `src/lib/admin-api-utils.ts` owns bounded page/page-size parsing and response metadata for Admin lists.
- Do not expand `/api/admin/overview` into a monolithic Admin record bootstrap.

### Admin Broker Detail

- `AdminBrokerDetailWorkspace.tsx` loads overview identity/counts, then only the active section endpoint.
- `src/lib/admin-broker-detail-server.ts` owns scoped selects, server filters, counts, pagination, and row hydration.
- Activity discovers relevant broker targets, queries/counts on the server, merges sorted sources, slices the requested server page, then hydrates only that page.

## Notification Architecture

- `public.notifications` is the persisted source of truth for Admin and broker feeds.
- Migrations `042_unified_notifications.sql` and `043_fix_unified_notification_read_state_triggers.sql` migrate/drop legacy tables and synchronize read state from listing, lead, and chat sources.
- `src/lib/notifications-server.ts` owns cursor encoding, bounded pages, unread/total/priority counts, creation, read state, and handled state.
- `src/lib/notifications.ts` owns shared payload types, sorting, Realtime reconciliation, and page merging.
- `/api/admin/notifications` and `/api/dashboard/notifications` authorize recipients and return cursor pages.
- `useAdminPriorityNotifications`, `useBrokerNotificationFeed`, and `useRealtimeNotificationRefresh` consume the unified feed.
- Loaded item count, `unreadCount`, `totalCount`, priority counts, and `hasMore` are separate values. Never derive one from another.
- Do not reintroduce `admin_priority_queue_notifications` or `broker_notifications`.

## Performance Boundaries

- Requirement match preview uses `fetchRequirementMatchCandidateListings`, lightweight listing fields, and prefiltered area/budget/bedroom candidates. Full hydration is reserved for flows that render full listing details.
- Buyer Board `/api/requirements` keeps ordinary sorts paginated at the database and can skip repeated static metadata with `includeStatic=0`.
- Listing browse `/api/listings` uses server filters/counts, bounded candidate/comparable reads, and hydrates only displayed listing IDs.
- Listing detail uses `src/lib/listing-detail-server.ts` and detail RPC/fallback paths.
- Public overview returns bounded latest listings and lightweight auth hydration via `scope=auth-me`.
- Middleware coalesces short-lived site-mode and user-access lookups. `auth-hydration.ts` coalesces short-lived profile hydration; `session-sync.ts` deduplicates cookie writes.
- Fix query scope, select size, pagination, and hydration before adding or increasing caching.
