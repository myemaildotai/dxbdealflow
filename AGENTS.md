# Repository Guidelines

## Project Overview

DXB Deal Flow is a private Dubai real-estate deal exchange with public discovery, approved-broker workspaces, and admin moderation. The installed stack is Next.js `14.2.32` App Router, React 18, strict TypeScript, Supabase, MUI 5, and Tailwind CSS 3.

## Source Of Truth And Scope

- Treat current source code, runtime configuration, and ordered Supabase migrations as authoritative.
- Use `AGENTS.md`, `.agents/codebase-index.md`, `.agents/skills/*.md`, Graphify output, and historical documents only as navigation aids.
- Keep changes scoped to the requested files and direct dependencies. Do not change UI, APIs, business logic, migrations, or dependencies unless the task explicitly requires it.
- Never revert unrelated worktree changes.

## Architecture Overview

Routes, layouts, pages, and handlers live in `src/app/`; `src/app/api/**/route.ts` owns server operations. Browser Supabase access is in `src/lib/supabase.ts`; server auth, clients, shared selects, and response helpers are in `src/lib/deal-server.ts`. Shared server data lives primarily in `platform-server-data.ts`, `broker-dashboard-server.ts`, `admin-broker-detail-server.ts`, `requirements-server.ts`, `listing-detail-server.ts`, and `notifications-server.ts`.

Root `middleware.ts` performs coarse site-mode, canonical-route, and blocked-broker gates. APIs must still authorize every operation.

## Canonical Route Conventions

- Admin workspace routes are `/admin`, `/admin/listings`, `/admin/requirements`, `/admin/chats`, `/admin/enquiries`, `/admin/activity`, and `/admin/leads`.
- Admin broker detail routes are `/admin/brokers/[userId]` plus `/listings`, `/requirements`, `/enquiries`, and `/activity`.
- Broker dashboard routes are `/dashboard`, `/dashboard/listings`, `/dashboard/enquiries`, `/dashboard/chats`, `/dashboard/requirements`, and `/dashboard/profile`.
- Use `src/lib/admin-routes.ts` and the dashboard route maps in `DashboardSectionPageClient.tsx` for navigation. Legacy query-based admin/dashboard navigation is redirect-only compatibility and must not be generated by new code.
- Route segments select the active workspace. Each section fetches its own dataset; do not restore tab-driven monolithic page loading.

## Performance-First Endpoint Rules

- Keep overview and shell endpoints lightweight. `/api/admin/overview`, `/api/admin/brokers/[userId]/overview`, and `/api/dashboard/shell` may provide shared metrics or identity context, but must not absorb section recordsets.
- Use scoped section endpoints under `/api/admin`, `/api/admin/brokers/[userId]`, and `/api/dashboard`. Treat `/api/dashboard` and the monolithic `/api/admin/brokers/[userId]` handler as compatibility-only; do not expand them or build new callers on them.
- Keep filtering, sorting, counts, and pagination server-side for admin lists and broker-detail sections. `/api/admin/brokers/[userId]/activity` must remain server-paginated.
- Prefer explicit selects, bounded reads, targeted RPCs, batched hydration, and parallel independent queries. Avoid broad `select("*")`, unbounded reads, duplicate requests, and full hydration when summaries are enough.
- Requirement match preview must use lightweight candidate listing fields and must not call full listing hydration. Buyer Board, dashboard, public overview, and browse endpoints should return only the data their current UI needs.
- Preserve listing browse/detail and requirements performance behavior and existing UI contracts.
- Do not use caching as the primary fix for an oversized query, unnecessary hydration, or duplicate data flow. Reduce the work first, then use existing cache/coalescing helpers where appropriate.

## User Roles And Access Control

- Public visitors browse visible active listings and submit enquiries; never expose broker-only data.
- Brokers require role `broker` and status `active` or `approved`; other statuses remain blocked.
- Admin routes and actions require role `admin`.
- Preserve role-based access across Public, Broker, and Admin flows. Use `requireApprovedBroker`, `requireAdmin`, `getRequestUser`, and `src/lib/route-access.ts`; never rely only on client guards or middleware.
- Never trust a submitted user ID, role, ownership claim, or status. Resolve identity from the verified token.

## Notifications

- The unified `notifications` table is the persisted source of truth for admin and broker notification feeds.
- Use `src/lib/notifications.ts`, `src/lib/notifications-server.ts`, `/api/admin/notifications`, and `/api/dashboard/notifications`.
- Notification list pagination is cursor-based and independent from `unreadCount`, `totalCount`, and admin priority counts. Do not infer totals from loaded items.
- Preserve Realtime updates, read/handled state, active/dismissed status, entity links, and recipient authorization.
- Do not reintroduce legacy `admin_priority_queue_notifications` or `broker_notifications` tables or new readers for them.

## Project Structure

- `src/app/`: App Router pages, layouts, loading states, and APIs.
- `src/components/`: reusable Public, Broker, Admin, and shared UI.
- `src/auth/`: session, auth hydration, and auth operations.
- `src/hooks/`: reusable client hooks, including notification and query hooks.
- `src/lib/`: business rules, server access, pagination, notifications, caching, email, and utilities.
- `src/theme/`: brand and MUI theme. `public/assets/`: static and email assets.
- `supabase/migrations/`: ordered SQL. `supabase/templates/`: Supabase email templates.

## Task Size And Context Selection

Choose one primary `.agents/skills/*.md` guide by default. Add one supporting skill only when a second domain is materially changed.

- Small task: read `AGENTS.md`, `.agents/codebase-index.md`, and one relevant skill. Inspect direct task files only. Do not use Graphify.
- Medium task: inspect the related module entry points and direct dependencies. Do not broaden into unrelated modules or use Graphify.
- Large task: begin with one primary skill. Use Graphify only for cross-module, unclear-impact, architecture, shared-contract, or broad performance work.

For qualifying Graphify work, inspect `graphify-out/GRAPH_REPORT.md` and `manifest.json` first, compare the graph commit with `git rev-parse HEAD`, and verify all conclusions against current source. Do not manually edit generated Graphify output.

## Database And Supabase Rules

Supabase provides Auth, PostgreSQL, Storage, Realtime, and RPCs. Preserve RLS assumptions and use request-scoped anon clients when RLS should enforce caller access. Service-role clients bypass RLS and are server-only; never expose `SUPABASE_SERVICE_ROLE_KEY`.

Never modify schema or create a migration unless explicitly requested. When requested, add the next ordered descriptive SQL file after `043_*`; never rewrite applied migrations. Make SQL idempotent where practical and document rollout and rollback risks.

## Feature Safety Rules

- Listings: preserve public visibility, ownership, moderation, credits, media/documents, internal-field visibility, enquiry routing, and cache invalidation.
- Requirements: preserve active-broker access, ownership, active/inactive state, soft deletion, admin deactivation, matching, notifications, and own-listing exclusion.
- Chat: preserve participant authorization, listing scope, cursor pagination, message sequences, idempotency, read markers, optimistic updates, Realtime, and read-only admin inspection.
- Email: preserve server-only SMTP delivery, templates, event-key deduplication, throttles, cron authorization, absolute asset URLs, and text fallbacks.
- Auth and site modes: preserve Supabase Auth, `dx-access-token`/`dx-refresh-token` cookies, session-write deduplication, auth hydration coalescing, broker verification, site-mode coalescing, and default-route behavior.
- Responsive work: preserve desktop behavior unless explicitly requested and reuse existing theme, shell, loading, empty, and modal patterns.

## Coding Standards

Maintain strict TypeScript; avoid `any`. Use two-space indentation, double quotes, semicolons, `@/*` imports, PascalCase components, `use`-prefixed hooks, and Next route filenames. Reuse existing utilities and types before creating new ones. Keep service-only code out of client bundles and validate API input server-side.

## Development And Validation

- `npm run dev` / `npm run dev:port`: start development.
- `npm run lint`: run Next ESLint.
- `npx tsc --noEmit --pretty false`: run strict TypeScript validation.
- `npm run build`: verify production types and routes.
- `npm run index:codebase`: regenerate the baseline `.agents/codebase-index.md`.
- `npm run index:check`: verify the codebase index exists and is not empty.

For application or runtime changes, run lint, TypeScript, and build, then verify affected Public, active-broker, blocked-broker, and Admin flows. For context-only changes, run `npm run index:check`; run the broader commands when explicitly requested.

## Agent Instructions

Before coding, read `.agents/codebase-index.md` and the most relevant skill, then inspect only the task entry points and direct dependencies allowed by task size. Analyze the affected data flow, API and Supabase dependencies, role impact, pagination, hydration, and notification behavior before editing.

After application changes, summarize changed files, validation, and remaining risks. Regenerate `.agents/codebase-index.md` after significant source-structure changes, then restore any repository-specific architecture notes that the baseline generator does not emit.
